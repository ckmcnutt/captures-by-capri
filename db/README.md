# Database

Local Postgres 17.6 + pgAdmin run via `docker-compose.yml` at the repo root.
17.6 matches the Supabase-hosted version this project migrated off (17.6.1.127).

## Layout

| Path | Purpose |
|---|---|
| `dump/` | **gitignored.** Drop the production `pg_dump` here. |
| `seed/` | **gitignored.** `data.sql` extracted from a restored dump. Contains customer PII. |
| `sql/100_rewrite_photo_urls.sql` | Rewrites `photo.url` from Supabase Storage URLs to `/media/` paths. |
| `sql/110_sync_sequences.sql` | Fast-forwards id sequences past `max(id)`. Mandatory after a data-only load. |
| `pgadmin/servers.json` | Pre-registers the local server in pgAdmin. |

Schema definitions live with the code that uses them, in
`artifacts/api-server/src/db/schema.ts`, with migrations in
`artifacts/api-server/drizzle/`.

## Commands

```bash
pnpm db:up          # start postgres + pgadmin, wait for healthy
pnpm db:down        # stop (keeps the data volume)
pnpm db:reset       # DESTROY the volume, recreate, migrate, seed  <- clean slate
pnpm db:psql        # interactive psql
pnpm db:restore     # restore db/dump/<newest> (re-runnable)
pnpm db:extract     # dump current data to db/seed/data.sql
pnpm db:migrate     # apply Drizzle migrations
pnpm db:generate    # generate a migration from schema.ts changes
pnpm db:studio      # browse data at local.drizzle.studio
```

- Postgres: `localhost:5433`, user/password/db all `capri`
- pgAdmin: <http://localhost:5050>, login `dev@local` / `dev`

`DATABASE_URL=postgres://capri:capri@localhost:5433/capri`

Note pgAdmin connects to `postgres:5432` over the compose network, **not** the
host's `5433`.

## Two paths, one schema definition

**Local dev / CI** — reproducible, no dump required:

```bash
pnpm db:reset       # migrations build the schema, then seed + rewrite + setval
```

**Production cutover on the LXC** — adopt the existing database:

```bash
pg_restore …                   # full dump
pnpm db:migrate                # no-op: the baseline migration is idempotent
psql -f db/sql/100_rewrite_photo_urls.sql
psql -f db/sql/110_sync_sequences.sql
```

Both paths converge on the same migration history, so dev and production stay in
step from that point on.

## First-time restore

```bash
pnpm db:up
pnpm db:restore                    # or: pnpm db:restore path/to/dump
bash scripts/db/inspect.sh         # READ THIS OUTPUT before writing code
pnpm db:pull                       # generate schema.ts from the real catalog
pnpm db:extract                    # capture data-only SQL for db:reset later
```

`scripts/db/inspect.sh` exists because three schema facts change how the code
must be written, and none of them are visible in the old generated Supabase types:

1. **Is `appointment.id` `GENERATED ALWAYS`?** If so the Cal.com webhook's
   explicit-id insert fails outright — it needs `OVERRIDING SYSTEM VALUE`, which
   Drizzle does not emit. It must be `serial` or `GENERATED BY DEFAULT`.
2. **Are the time columns `timestamptz` or bare `timestamp`?** Bare `timestamp`
   means the scheduler's day-window arithmetic compares wall-clock against UTC.
3. **Do status ids 2 and 12 really mean `appointment_canceled` and
   `appointment_rejected`?** The old edge function hardcoded them. If they don't
   match, production has been writing the wrong status.

## Migration workflow

```bash
# 1. edit artifacts/api-server/src/db/schema.ts
pnpm db:generate     # 2. writes drizzle/NNNN_*.sql
# 3. READ the generated SQL. Always.
pnpm db:migrate      # 4. apply
```

**Never run `db:push` against production** — it applies a schema diff without
recording a migration, so the history silently diverges. It exists for local
experiments only.

After `db:pull` plus the baseline, `db:generate` must report **no changes**. If it
wants to alter something, `schema.ts` does not faithfully describe the database and
every future migration will carry that drift.

## Gotchas

- **`appointment.id` is both a serial PK and a sink for Cal.com booking ids.**
  Webhook-created rows set the id explicitly, which never advances the sequence.
  `110_sync_sequences.sql` is mandatory after a data-only load, and the
  appointments repository bumps the sequence after every explicit-id insert.
- **A data-only restore does not carry `setval`.** Skipping
  `110_sync_sequences.sql` means the next insert collides immediately.
- **A full Supabase dump is noisy** — it references `anon` / `authenticated` /
  `service_role` roles and the `auth` / `storage` / `extensions` schemas. Prefer
  `pg_dump -Fc --no-owner --no-privileges --schema=public`. If you must restore a
  full dump, read the errors rather than assuming they're benign: a failed
  `CREATE TABLE` hidden among 200 role errors leaves a half-restored database.
- **RLS policies are inert here.** The app connects as an owner-equivalent single
  role, so policies were not ported. Don't reintroduce them expecting enforcement.
- **`db/dump/` and `db/seed/` hold customer PII** and are gitignored.
  `scripts/db/extract-data.sh` refuses to run if that ever stops being true.
